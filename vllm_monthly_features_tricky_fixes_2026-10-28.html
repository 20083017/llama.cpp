三、最 Tricky 的 Fixed Issues：根因与方案

3.1 已进入 v0.32.0 的修复

1. #50300 · 恶意 Jinja chat template 造成资源耗尽 DoS

Security / API

CPU / 内存耗尽 认证客户端可提交包含超大 range()、字符串乘法或深层嵌套循环的模板；同步渲染还会堵住共享 async runtime。

根因把模板当成可信配置，而未把它视为可执行、可消耗无上限资源的输入；仅做语法解析无法限制运行成本。
方案Python 侧增加 AST 静态规则与可配置渲染超时，Responses 拒绝用户传入模板；Rust 侧以 50 万指令 fuel 限制执行，并用 spawn_blocking 隔离同步渲染。属于“静态拒绝 + 动态预算 + 隔离”的纵深防御。

关联 GHSA-4hhp-h66f-j5j7。修复评审还处理过超时后 executor 生命周期问题，说明安全修复本身也必须做后续请求回归。

2. #59491 · tokenizer max_token_id 的 off-by-one 可杀死引擎

Security / 边界

CUDA assert 当词表大小为 32,000 且没有 padding 时，非法 token ID 32,000 能通过校验，并在 TP=1 embedding 查找中触发 CUDA assert。

根因vocab_size 是“数量”，最大合法 ID 应为 vocab_size - 1；是否实际崩溃还取决于词表 padding 和 TP 索引屏蔽，所以并非所有模型都暴露。
方案把回退值改为 vocab_size - 1，但仍优先使用 get_vocab() 的真实最大 ID，避免误伤 Qwen 等包含 added tokens 的模型。

验证：195 项指定测试通过；GPT-2 最大值由 50257 修正为 50256，Qwen2.5 仍保持 151664。

3. #51504 · 从未连上的 P2P peer 永久占用 ZMQ sockets

Security / 分布式生命周期

EngineCore 退出 客户端通过 kv_transfer_params 提交唯一且不监听的 peer，每个残留约 3 个 socket；约 340 个 peer 即可耗尽 ZMQ 的 1,023 上限。

根因原清理依赖 DISCONNECTED，但“连接从未建立”的 peer 不产生这个事件，因此永远不进入普通断连回收路径。
方案五层防护：peer 上限 128、握手 30 秒、空闲 300 秒、session 创建异常边界、补充 CLOSED 和 HANDSHAKE_FAILED 等 fatal monitor 事件；同时增加 idle reaper。

参数：VLLM_P2P_MAX_PEERS、VLLM_P2P_HANDSHAKE_TIMEOUT_S、VLLM_P2P_IDLE_TIMEOUT_S。195 项 P2P 测试通过。

4. #59357 · 共享内存多模态缓存句柄可伪造且会在 clear 后别名

Security / 跨进程对象身份

不可信反序列化 --mm-processor-cache-type shm 曾信任客户端提交的共享内存 address/ID；clear() 重置 ID 还会让旧句柄指向新对象。

根因address+ID 只是定位信息，不具备不可伪造性；ID 重用又破坏“句柄永远指向同一逻辑对象”的生命周期假设。
方案服务端生成随机 32 字节 secret，对 cache key、address、ID 做 HMAC；读、写、touch 和 scale-out 输入都验签并检查边界。clear 后不再重置 ID，使旧句柄在槽位复用时失效。

74 passed、1 skipped，覆盖缺失/篡改/错误 key 签名、越界字段、clear 前旧句柄和 scale-out 验证；默认 LRU cache 不受影响。

5. #59042 / Issue #58729 · EP 下 token 被静默路由到错误专家

MoE / 分布式编号域

静默错误 CUTLASS NVFP4/MXFP4 MoE 在 EP 下输出退化，GLM-5.3-MXFP4、DP/EP=8 的 GSM8K 曾接近 0%，但没有崩溃或明确报错。

根因实现接收 expert_map 却不使用。topk_ids 仍是全局专家编号，而当前 rank 的权重是本地分片；把全局 ID 直接当本地数组下标，数学计算正常执行，语义却完全错误。
方案grouped GEMM 前通过 Triton kernel 将全局 topk_ids 重映射为本地 ID，复用已有 remap 实现并增加 int32/int64 输出；只对支持的 EP 通信后端开放，其他组合 fail fast。

修复后 GSM8K flexible-extract 达 95.07%；remap 开销约 1.6 µs，约为 GEMM 的 1%。这类问题必须用精度评测和分布式配置覆盖，单元 kernel 对拍不足以发现。

6. #60614 · 调试引用把 Phi-4 音频临时注意力变成跨请求内存滞留

多模态 / 内存生命周期

CUDA OOM 合法最长音频可让 24 层共同滞留数 GiB 注意力矩阵，请求结束后仍不释放，最终 EngineCore 死亡。

根因eager attention 为调试把完整概率矩阵保存到每层模块的 self.attn。临时计算结果因此获得长生命周期引用，Python/PyTorch 无法回收。
方案删除模块上的 self.attn 保留，默认改用 SDPA（Scaled Dot-Product Attention），避免实体化完整稠密注意力矩阵，同时保留 eager 路径但不再残留。

两项回归测试分别覆盖默认 SDPA 和 eager 无残留。难点是 OOM 发生在后续请求，真正的引用却在之前请求中建立。

7. #61718 / Issue #61603 · Mamba2 在 SM90 随机整行 NaN

Triton / 异步 WGMMA 竞态

间歇 NaN 有限输入也会间歇产生 NaN/Inf；进程重启后可能“时好时坏”，因为 autotune 每次只按速度重新选配置。

根因特定 num_warps/BLOCK_SIZE_M/num_stages 组合让 Triton 生成异步 WGMMA；上一轮尚未等待完成，下一轮便覆盖其 A 操作数寄存器，违反 PTX ISA 约束。竞争本身随机，autotune 又把“选到坏配置”变成跨进程随机事件。
方案仅 CUDA SM90 从实际 autotune 列表过滤危险配置：warps 为 4 的倍数、M 为 64 的倍数且 stages>1。不是只删除已观测失败的几个配置，也不影响 ROCm 或其他 GPU。

23 个配置中过滤 11 个；坏配置从 8/23 变为 0/12，95 项测试通过。1024/8192 长度最佳耗时保持 62.2/425.4 µs；未跑端到端服务，底层 Triton bug 属于规避而非编译器修复。

3.2 仅在 main 的疑难修复

8. #60553 · encoder cache 与 speculative lookahead 相互等待形成死锁

Scheduler / 多模态

永久 0 token encoder cache 只能容纳一张图，且两图间距 gap < 2 × lookahead 时，请求永久无法调度，没有错误日志。

根因释放逻辑要等到 end1 + L 才释放图 1；分配图 2 失败时，调度却在 start2 - L 截断。当 start2 - L < end1 + L，计算位置永远到不了释放点，图 2 也永远分不到缓存。
方案两处都去掉 L 偏移：按真实 item end 释放，分配失败时停在 start2；边界处由 runner 已有路径回退到 token embedding。只修一边只会把死锁窗口从 gap<2L 缩到 gap<L。

GB200 上 gap=0/1 从 300 秒挂起变为完成，温度 0 输出与无推测基线一致。代价是缓存满时边界最多 L 个位置使用 token embedding，可能略降一步接受率。

9. #62164 / Issue #62121 · 跨线程 cache invalidation 插入 lookup 与 merge 之间

Async / 多模态缓存

Expected a cached item asyncio 线程处理 engine cache-miss 时，可在单 worker renderer 的 lookup 和 merge 之间删除 entry，产生 HTTP 500。

根因缓存读取与失效没有共同的线性化边界；简单加一把大锁又可能阻塞输出流，朴素排队则会被不存在的 hash 或重复通知撑大。
方案miss 先写入 pending set，在下一次 render 查缓存前统一交换并应用；过滤未知 hash、合并重复通知，失败时恢复尚未处理的集合，同时保留新到通知。

历史 A800 压测目标断言从 18 降为 0；最终版 57 passed、1 deselected。PR 明确说明该压力数据对应历史提交，最终清理版另有 sleep/wake 与真实 renderer 验证，不混同为同一次测试。

10. #63118 · nvcc 优化与 NaN 排序不一致最终导致 shared-memory 越界

CUDA / 编译器与数值

Illegal memory access ≥64K 列且 NaN 数超过 top_k 时，cooperative_topk 崩溃；warmup/CUDA graph capture 读取未初始化 KV 时可能遇到这种输入。

根因nvcc 将整数位操作 bits | 0x80000000u 优化成 FP -|x|。有限值位级等价，但 FADD 会把 NaN 规范化为 -0.0 的 key；粗排却把 NaN 排在 +inf 之上。两套顺序冲突产生错误 pivot，使无界 append 写穿 shared memory。
方案用 opaque mov.b32 读取原始位，阻止编译器把整数位操作改写为 FP 运算；粗排和精确恢复因此都把 NaN 排在 +inf 之上，并复用到相关 top-k 路径。

compute-sanitizer 定位 shared OOB；新增 64K～1M 列、每行 4×top_k NaN 的溢出回归和多组 torch 对拍。这个案例不能靠“忽略 NaN”解释，因为编译器、排序和内存安全构成了一条完整因果链。

四、工程经验与升级建议

问题模式需要守住的不变量推荐验证
EP / 分片计算全局逻辑 ID 与本地物理 ID 必须在边界显式转换。DP/EP>1 的真实模型精度评测；禁止只看 kernel 是否执行成功。
autotune / 异步 GPU性能搜索空间必须排除已证明不满足硬件时序约束的配置。逐配置重复运行、finite/closeness 检查、跨进程重启；不能只测 autotune 最终选中的一个配置。
缓存与 lookahead释放条件和分配/截断条件必须能从同一进度变量推导，不允许循环等待。对 gap、lookahead、cache capacity 做二维/三维 sweep。
跨线程缓存失效lookup/merge/invalidation 要有明确线性化点，通知队列必须有界。强制交错、重复 miss、未知 hash、失败恢复和持续背景流量。
共享内存与跨进程句柄定位信息不等于授权；句柄需认证且不能被 ID 重用重新解释。伪造签名、越界字段、clear 后旧句柄、scale-out 输入。
不可信模板 / peer所有执行和连接都需资源预算、超时与回收，包括“从未成功建立”的状态。恶意模板、握手失败、空闲超时、后续正常请求存活。
P0 · 安全与兼容：优先采用包含 #50300、#59491、#51504、#59357 的 v0.32.0 或更新版本。升级前核对 Python 3.11+、Transformers 版本区间、浏览器端 --allowed-origins、Responses 事件和 max_tokens 客户端语义。
P1 · 性能上线：低精度 KV 要同时测显存、TTFT、TPOT 与精度。GLM-5.x SM100 的 FP8 KV 默认变化不是“纯收益”；HiSparse 的 58% 和 API worker 的 43%～85% 都有明确负载前提。
P1 · 回滚策略：稳定生产保留 v0.31.0/v0.32.0 对应容器、依赖 lock 和配置。main 功能应按 PR 单独开启，例如 KV-balanced MLA 是 opt-in；遇到问题时关闭新 backend 比回滚整个 serving 栈更容易定位。

五、术语速查

KV cache缓存历史注意力 Key/Value，长上下文和高并发下是主要显存消耗。NVFP4 / MXFP4 / FP8不同 4-bit / 8-bit 浮点或微缩放格式，用于权重、激活或 KV 压缩。
MLAMulti-head Latent Attention，多 latent 注意力；通过低秩表示降低 KV 存储与计算。MRV2Model Runner V2，vLLM 新一代模型执行路径。
TP / DP / PP / EP / PCP张量、数据、流水线、专家、prefill context 等并行维度；各自切分对象不同。TTFT / TPOT首 token 时间 / 后续每输出 token 时间，应分别评估。
