3. llama.cpp candidates

#30879 · Sarvam byte-fallback tokens are labeled NORMAL instead of BYTE

Best first PR · S

Tokenizer metadata Tokens <0x00> through <0xFF> are written as NORMAL. Unicode containing ₹ and a narrow no-break space can decode into literal byte-token text; relabelling fixed decoding without changing tokenization.

ImplementationIn conversion/bailingmoe.py, mark the model's 256 byte-fallback tokens as BYTE, preferably by deriving them from tokenizer metadata/patterns rather than depending only on fixed IDs.
ValidationBuild a vocab-only GGUF; assert all 256 token types; round-trip Unicode byte fallback and ASCII; confirm ordinary tokenization and model scores are unchanged.

PR audit: no PR reference found in the all-state title/body search on 2026-10-29. A commenter offered to prepare a fix, so coordinate in the issue first.

#30422 · Pooled reranking copies unused n_vocab logits to the host

Performance · S/M

Large measured win Qwen3-Reranker copies roughly 600 KB of logits per token. The reporter measured 2,119 MB DtoH traffic for one request and local rerank improvements from 3.10 s to 0.53 s and 35.1 s to 5.3 s, with identical scores.

ImplementationIn src/llama-context.cpp, avoid raw-logit host extraction for pooled-embedding batches while preserving completion logits on mixed-use servers. Keep avoiding LM-head graph construction as a separate optimization if it expands scope.
ValidationCompare rerank scores, measure DtoH bytes with nsys, alternate rerank and completion requests, and test pooled/non-pooled paths on at least CPU and CUDA.

PR audit: no direct PR found on 2026-10-29. Maintainer feedback is still absent, so keep the first patch narrow and include mixed-workload tests.

#30773 · Responses API marks truncated tool calls complete

API correctness · M

Protocol semantics With max_output_tokens=40, streaming can return incomplete JSON arguments yet emit response.completed and item status completed. Successful calls also omit function_call_arguments.done. Chat Completions correctly reports finish_reason: length.

ImplementationIn tools/server/server-task.cpp, propagate the existing stop reason through Responses serialization; emit response.incomplete with incomplete_details.reason=max_output_tokens, do not complete truncated items, and emit argument-done events for finished calls.
ValidationAdd SSE event-sequence tests for complete/truncated text and tool calls, malformed-JSON truncation, non-streaming Responses, and stop-reason parity with Chat Completions.

PR audit: no PR reference found on 2026-10-29. A second user independently reproduced both defects, strengthening the report.

#30954 · RPC + Vulkan tensor splitting frees temporary tensor metadata too early

Backend lifetime · M

Multi-worker crash Two-worker RPC/Vulkan tensor splitting segfaults while layer splitting and individual workers succeed. Reporter follow-up implicates temporary tensor contexts in comm_allreduce() and uncached graph_compute().

ImplementationInspect ggml/src/ggml-rpc/ggml-rpc.cpp. Either synchronize temporary graphs before context destruction or retain tensor metadata until backend completion. Compare the synchronization cost with an ownership-based fix.
ValidationRun two/three/five workers, reversed worker order, GGML_RPC_NO_COMM=1, repeated tensor-split generation, layer-split control, ASan, and output parity.

PR audit: no PR reference found on 2026-10-29. Root cause is strongly supported but the preferred ownership design remains unconfirmed.

#31229 · Op-offload batch heuristic counts heads as tokens

Scheduler design · M

Unnecessary GPU islands Qwen3 per-head normalization MUL/ROPE nodes are offloaded separately from surrounding CPU layers, causing CPU→GPU→CPU transfers. Vulkan showed 73 splits versus one with a higher threshold; two tokens defeat that workaround.

ImplementationReview get_op_batch_size and device pinning around src/llama-context.cpp. Use token-based semantics for per-head elementwise operations or pin the normalization chain with its layer. Review the earlier heuristic revert in #19976 before choosing a global change.
ValidationInspect split graphs at one/two tokens on CUDA and Vulkan, cover Qwen3/Qwen3.5, run backend-op correctness tests and alternating performance runs with full-offload controls.

PR audit: no PR reference found on 2026-10-29. Reporter explicitly requests design guidance; discuss the invariant before changing the global heuristic.

4. vLLM candidates

#62558 · TurboQuant hybrid GDN block splitting and drafter page inflation

Quantized KV · M/L

Two related defects A 1,712-token manager block cannot be split into supported kernel blocks. After a local workaround, FP8 drafter pages force every page to the largest size, shrinking the KV pool from 235,605 to 97,517 tokens.

ImplementationSplit the work: (1) define correct non-power-of-two block-size semantics for TurboQuant/Triton paths; (2) choose drafter page divisors that fit unified page-size constraints instead of inflating all pages. The reporter already has env-gated local changes and measurements.
ValidationAdd generic block-size/page-unification unit tests plus ROCm integration. Verify startup, pool capacity, tool calls, output quality, and TRITON_ATTN block-size assumptions; do not mix in the separate gfx1201 FlyDSL tuning.

PR audit: no direct TurboQuant PR found. PR #40914 is a different spec-verify path. The reporter offered to turn the changes into a PR, so the best contribution may be collaboration, test coverage, or splitting one focused sub-fix.

#62626 · FULL CUDA graph + FA3 split-KV freezes the wrong combine scheduler

Advanced CUDA · L

Silent wrong logits Capture uses a dummy mixed batch, and FA3's combine kernel chooses a host-side tile scheduler/grid from that shape. Replay can then use a different real batch on the frozen grid, leaving output rows uncombined.

ImplementationPreferred direction: use a capture-safe LINEARIZE_M_AND_BATCH scheduler whose grid depends only on padded values stable across capture/replay. Alternative: capture with an upper-bound max_seqlen_q, but that can change main-kernel performance and needs separate evaluation.
ValidationRun the supplied q=2 prefix-cache repro, mixed-batch sweeps, split-cap controls, H100/H200, FULL versus FULL_AND_PIECEWISE, and FlashInfer controls. Assert logits against a non-captured path, not just absence of crashes.

PR audit: open PRs #64000 and #64205 mention this issue but explicitly do not fix its FULL-graph combine behavior; #64205 excludes full-CG-eligible batches. The issue remains a valid advanced contribution.

5. TensorRT-LLM candidates

#20944 · CUDA 13.4 JIT headers conflict with unbounded NVRTC 13.0

Packaging · S

Clean dependency contract The v1.4.0rc1 wheel accepts NVRTC 13.0 but bundles CUDA 13.4 headers that reference unknown identifiers. Loading NVRTC 13.4.92 makes the same benchmark compile and finish.

ImplementationDeclare a matching minimum nvidia-cuda-nvrtc version, or bundle headers compatible with the oldest supported NVRTC. Add an early loaded-NVRTC/header compatibility error so future mismatches are actionable.
ValidationTest a clean pip + torch cu130 environment, inspect wheel METADATA, and run the B300 FMHA JIT warmup. Also test the supported oldest NVRTC and the official container path.

PR audit: PR #20945 fixes only nvcc path selection (#20515) and explicitly leaves this NVRTC/header issue out of scope.

#20988 · Per-request video kwargs allow multi-GiB decoded allocations

Serving hardening · S/M

CPU-only repro A 1.2 MB video plus client-supplied num_frames=500 produced 5.15 GiB of float32 data and 12.2 GiB peak RSS; 1,000 frames attempted an 11 GiB allocation. Encoded-size limits do not bound decoded size.

ImplementationApply server-authoritative limits before stacking/conversion: cap request num_frames by server policy and/or reject excessive frames × height × width × channels × dtype. Preserve explicit server configuration while preventing clients from raising the limit.
ValidationUse the supplied tiny-video repro, boundary frame counts, multiple video parts, fps×duration paths, and normal requests. Test both rejection and accepted-control behavior without requiring a GPU.

PR audit: no PR reference found on 2026-10-29. The exact policy needs maintainer agreement, but the fix can start with decoded-byte enforcement.

#20969 · Dense Qwen3.8 NVFP4 misses the Hopper Marlin default

Model defaults · S/M

Existing pattern to reuse Dense Qwen3.8 NVFP4 fails during warmup on SM90 because the default backend list lacks Marlin. Explicitly allowing Marlin starts and produces sensible GSM8K results; Qwen3.5 MoE classes already select Marlin on SM89–99.

ImplementationGive dense Qwen3_5ForCausalLM and the VL defaults the same NVFP4/MIXED_PRECISION linear backend default as the MoE path, without importing the MoE backend choice.
ValidationCover dense and VL class resolution, NVFP4 and MIXED_PRECISION configs, SM89–99 default selection, and an H200 smoke/accuracy run. Confirm unrelated architectures keep their defaults.

PR audit: no direct PR found. Open PR #12591 only improves the early error message and does not change the default, so it is not a fix for this issue.

#20211 · KV estimation probe ignores explicit host-cache budget

Memory sizing · M

Startup OOM Estimation drops the explicit tier budget, then auto-sizes from device quota and node-wide free memory. Under a 16 GiB cgroup, a 1 GiB configured tier became a 17.37 GiB probe and was OOM-killed 6/6 times.

ImplementationFor the first focused PR, bound auto sizing by min(existing_auto_quota, configured_share) while preserving target/draft shares and the fleet minimum. Treat cgroup-aware automatic sizing as a separate design decision.
ValidationTest explicit cap, zero target/draft shares, missing cache costs, no-cap behavior, and multi-rank sizing. Add a cgroup integration test if available; do not claim cgroup correctness from CPU unit tests alone.

PR audit: no upstream PR found. A commenter has a prepared fork commit with 94 CPU regressions passing, so coordinate before implementing. Open #19650 changes commit timing, not the explicit-cap arithmetic.

#20647 · ENABLE_MULTI_DEVICE=OFF reaches undefined MPIPoolExecutor

Build/launch design · M

Design-first A single-GPU build fails on its default startup path because MPIPoolExecutor is imported only for multi-device builds but still referenced by MpiPoolSession.

ImplementationDiscuss two options: automatically select the existing in-process TP1 worker when MPI is disabled, or fail early with a clear configuration error. A fallback must reject multi-rank requests and preserve supplied sessions and explicit Ray/RPC choices.
ValidationBuild with ENABLE_MULTI_DEVICE=OFF, then test startup, generation, streaming, shutdown, postprocessing handoff, and invalid multi-rank requests. CPU-only routing tests are not enough for process-isolation changes.

PR audit: no direct upstream PR found. PRs #20580 and #13737 do not change this launch path. A fork proposal exists; settle process-isolation semantics with maintainers before submitting.
