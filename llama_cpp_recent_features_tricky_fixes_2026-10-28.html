一、结论先行

推理性能MoE 专家缓存成为本轮最实用的性能特性：把内存中的专家按 LRU（最近最少使用）换入 GPU，特定 RTX 5090 场景最高报告 2.20× 解码速度；随后演进为多 GPU 共享和 SLRU 分段缓存。
产品能力从“文本推理 CLI/服务”继续扩展到实时语音转写、TTS、全模态模型、模型发现下载、P2P 远程访问和会话压缩。
修复共性最棘手的问题并非单点算法错误，而是跨层不变量失效：GPU 同步、图与内存生命周期、融合后的别名、数值全定义域、缓存边界和整数符号。
升级兼容性提醒：v0.7.0 将 server 默认端口从 8080 改为 9931；格式化聊天输出由单字符串改为 parts 数组。依赖旧端口或旧响应结构的客户端要先适配。Docker 容器内部仍保留 8080。

口径：扫描 v0.7.0 到 b11944 的 275 个提交标题，并重点核对官方 Release、PR 与关联 Issue。下文是高价值筛选，不是 275 项逐条流水账。性能数字均来自 PR 作者的特定硬件、模型和参数，不应视为普遍收益承诺。

三、最 Tricky 的 Fixed Issues：根因与方案

以下按“跨层机制是否难发现、触发条件是否隐蔽、修复是否具有代表性”筛选，而不是按 PR 行数排序。事实上，多处关键修复只有 1～3 行。

1. #30243 · 正则替换被长输入变成远程栈溢出

Server / 安全健壮性

崩溃 不可信输入 /v1/systemone 在 Linux 处理 d1-omni 请求时，形如 <| 加 30,000 个字母的 state 会让 HTTP 线程 SIGSEGV；macOS 的 libc++ 不受影响。

根因libstdc++ 的 std::regex_replace 对名称逐字符递归，调试显示每字符约 3 个栈帧，8 MB 栈被耗尽；而且转义发生在请求大小检查之前。
方案用线性手写扫描器替换正则，保持相同 <|name|> 转义语义，每字节最多读取两次；不是简单放大栈或加输入阈值。

验证：19,531 个短字符串与旧正则做差分，另测 100 万字符名称；旧实现会崩溃，新实现返回正常的“输入过大”HTTP 500 且服务存活。相关深层 JSON 嵌套由 #30242 单独处理。

2. #30107 · Vulkan TOP_K：非有限值让搜索进入未初始化状态

GPU / 数值全定义域

设备复位 错误索引 +inf/NaN 未被桶计数后，NVIDIA 可挂起到驱动复位，AMD 返回错误索引；另一个独立问题是 k=1 时全负值排序反向。

根因浮点被映射为有序 uint 后分桶缩小范围，但初始区间上界刚好排除 +inf 和 NaN；没有桶达到阈值后，shader 继续使用未初始化 shared state。k=1 快路径又把 float 位模式当有符号整数比较，负值顺序因此颠倒。
方案读取时把 NaN 映射为 -inf；初始范围扩到整个 uint 域；对顶端桶的 2³² 终点做钳制避免回绕；k=1 改为直接比较 float。

验证：新增 +inf、-inf 和负值用例后，Radeon 上 TOP_K 从 525/531 变为 531/531。NaN 不与 CPU 的未定义排序结果做对照。

3. #26771 / Issue #26738 · CUDA Graph 重放已经归还给驱动的地址

GPU / 生命周期

Page fault 窄条件组合 深上下文、legacy pool（无 VMM）、启用 graphs、-fa 0、MoE 部分 CPU offload 和足够碎片同时出现时，pool flush 后 GPU 访问不存在页面。

根因CUDA Graph capture 固定记录 scratch buffer 地址；分配器 clear_pool()/cudaFree 只知道内存被释放，不知道已捕获图仍保存地址，后续 replay 向 stale pointer 写入。
方案在“分配失败后的 clear_pool”和“pool 满时的 cudaFree”两条真实释放路径上，按 context 清空 CUDA graphs，强制下次重新 capture；避免跨设备过度失效。

验证：ROCm Vega 56 同一 benchmark 的 5 次 flush 都触发图重捕获并完成；与关闭 graphs 的绕行方案相比性能无回退。pool-full 第二路径未能实际构造，作者明确标为未实测。

4. #30573 · Flash Attention 缺少“读后到下次写前”的 WAR 屏障

CUDA / 并发

潜在错值 测试全绿也会出错 hsk=256、nb=1 时 compute-sanitizer 报 WAR（Write After Read，写后读反向时序） hazard，但作者尚未观察到错误输出。

根因KV 循环复用 shared KQ buffer。已有 warp barrier 只保证“写分数完成后再读并累积 V”，却没有阻止部分 lane 在下一轮提前覆盖其他 lane 仍在读取的位置。
方案在循环末尾增加 ggml_cuda_syncwarp()，保证所有 lane 读完再进入下一轮写。由于访问限制在写入 warp 内，warp barrier 足够，无需更重的 block 同步。

验证：RTX 3090 racecheck 的 8,007,424 条 WAR 警告降至 0；完整 FLASH_ATTN_EXT 3,993/3,993 通过。修复前 38 项选定正确性测试也全过，说明 sanitizers 不可替代。

5. #30795 · Metal 融合把合法内存复用变成同 dispatch 竞态

Metal / 图优化与别名

罕见非确定错值 融合 MOE_REDUCE 同时读取 experts/weights 并写 dst；当 dst 与输入别名时，不同 threadgroup 会并发读写同一内存。

根因分配器按未融合图计算 tensor liveness：早期节点已完全消费输入，因此把输入内存回收给 dst 原本合法。融合后多个阶段变成单次 dispatch，原来的生命周期假设不再成立。
方案encode 时用 ggml_metal_fusion_overlap 检查 dst 与 experts 或 weights 是否重叠；重叠就拒绝融合，回退始终正确的未融合 MUL+ADD，而不是试图保留高风险优化。

验证：kolibri 架构路径可复现。这个案例的关键是“优化改变并发与生命周期语义”，不能只比较融合前后的数学公式。

6. #30106 / Issue #28637 · Vulkan tile 与 subgroup 宽度假设失配

Vulkan / 越界与漏算

跨 tile 越界写 硬件相关 subgroup-16 Mali 上小矩阵出现非确定错值；subgroup-8 的部分 ID tile 又会漏算行。

根因小 tile 的 WM 被固定为 32，或 8-wide subgroup 时固定为 8，没有同时满足 BLOCK_SIZE、WARP 和 subgroup 的 tiling 恒等式。Mali 上 workgroup 的第二个 subgroup 会写入下一个 tile 的列，形成 race。
方案按各 tile 参数推导 WM = 32 × WARP / BLOCK_SIZE，确保一个 subgroup 只负责一个 warp tile，消除跨 tile 写入和未覆盖区域。

验证：Pixel 9 上修复前 20 个 MUL_MAT、6 个 MUL_MAT_ID 失败，修复后全部通过。

7. #30580 · SWA 缓存恢复阈值多要了两个 cell

Server / 状态边界

性能回退 Gemma 4 slot restore 后，本应复用的状态被拒绝并回滚到更早 checkpoint，导致下一轮重复处理大量 token。

根因SWA（Sliding Window Attention，滑动窗口注意力）保存状态只保留窗口内 cell，起点为 pos_max - n_swa + 1。首个待评估 token 只需访问 pos - n_swa 之后的位置，但复用判断使用了更严的 pos_min < pos - n_swa，额外要求两个 cell。
方案让 SWA reuse threshold 与实际窗口语义一致；非 SWA 的 recurrent state 仍保留原来的精确边界，因为状态必须恰好结束在待评估 token 之前。

验证：slot save/erase/restore 后重算 token 从 71 降到 23；RAM prompt cache 会话切换从 53 降到 17，并新增窗口恢复回归测试。

8. #30453 · Meta arena 重分配后仍使用旧 subgraph

图执行 / 内存所有权

Segfault 容量组合依赖 多 GPU 张量切分实验中，后续 graph 即使仍处在 max_subgraphs/max_nnodes 限制内，也可能访问已释放或过小的 subgraph。

根因max_nnodes_raised 触发时没有完整重建后续 subgraph；另一种“subgraph 更多但节点更少”的情况又会按当前 n_nodes < max_nnodes 跳过重建，忽略 slot 数量或容量已不匹配。
方案arena 发生重分配时统一重建全部 subgraph，而不是只重建部分或仅凭节点数判断无需处理；添加覆盖两种容量组合的分配测试。

验证：新增 test-alloc 用例。难点多维容量各自看似合法，但对象实际地址与槽位容量已经变化。

9. #30135 · 负 offset 经无符号回绕绕过边界检查

Core / 整数与内存安全

OOB write ggml_acc/ggml_set 可在目标 buffer 之前读写 4 字节；RPC GRAPH_COMPUTE 路径也可能从线上复制未经验证的 op_params。

根因op_params[3] 实为 int32_t，却直接读入 size_t。-4 符号扩展成巨大无符号数，现有边界断言发生回绕后反而通过，最终写指针落到 dst 前方。
方案先按 int32_t 读取，断言 offset 非负，再转换为 size_t；应用于 acc_f32、set_f32 和 set_i32。关键不是再补一个更大的上限，而是先验证符号域。

验证：ASan 在 op_params[3]=-4 时原实现报告 heap-buffer-overflow；补丁后同一输入立即触发 GGML_ASSERT，阻止越界访问。

四、可复用的工程经验与升级建议

问题模式应检查的不变量推荐验证
共享内存 / 流水线不仅“写后才读”，还要“读完才能下一轮写”。racecheck/compute-sanitizer + 常规正确性套件；不能只看输出。
CUDA Graph / 缓存对象任何真实释放地址的路径，都必须让保存该地址的图失效。制造 pool flush、碎片、深上下文，并检查 recapture 日志。
图融合融合后重新审查 liveness、alias、同步和中间结果可见性。强制构造 dst/input 重叠；保留正确未融合回退。
GPU 数值算法输入域必须覆盖 ±inf、NaN、全负值和桶端点回绕。非有限值、边界值、多 subgroup、多后端对照。
KV / prompt cache恢复条件要由真实注意力窗口和状态语义推导，不能沿用通用阈值。统计恢复后的重算 token，而不只检查“恢复成功”。
外部输入与整数先验证符号和范围，再转换无符号类型；避免对不可信长输入使用递归正则。ASan、超长输入、恶意 op_params、差分测试。
P0 · 升级前：固定版本来源，明确使用稳定版还是预发布；适配默认端口 9931 和聊天 parts 输出。需要旧行为时可显式配置 --port 8080，不要依赖默认值。
P1 · 性能落地：MoE 大量 offload 且 decode 批量较小时，优先评估 --moe-cache-mib。从专家总量约 10% 起步做命中率与端到端 t/s 扫描；若不需要，移除该参数即可回退。不要把 2.2× 直接套到不同模型、PCIe 或批量。
P1 · 预发布验证：实时音频重点测首段音频竞态、客户端快于解码的背压、空闲休眠和多会话；P2P 重点审计外部 llama-connect、API key 和断线状态。生产回退最稳妥的方式是保留 v0.7.0/b11669 工件与旧配置，而不是只回退单个 PR。

五、术语速查

GGUFGGML Universal Format，llama.cpp 生态常用的模型权重与元数据格式。MoEMixture of Experts，混合专家；每个 token 只激活部分专家，权重常远大于实际每步计算量。
LRU / SLRU最近最少使用 / 分段最近最少使用缓存；后者把稳定与波动对象分段，降低缓存污染。MTP / DFlash / LiliCorr多 token 预测及草稿生成技术；草稿先提出候选，主模型验证并接受或拒绝。
KV cache / slot缓存历史注意力的 Key/Value；server 用 slot 管理会话状态与恢复。SWASliding Window Attention，滑动窗口注意力，只保留有限历史窗口。
CUDA Graph预先捕获 GPU 操作图并重复执行，降低启动开销，但会保存地址等资源假设。WAR / OOBWrite After Read，读尚未完成就被覆盖；Out of Bounds，越界访问。
