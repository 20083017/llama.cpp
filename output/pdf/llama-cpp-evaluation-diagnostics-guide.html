一、Roofline：资源占用该怎么测

先定性再定量：decode 阶段是 memory-bound（每 token 读全部权重一次），prefill 是 compute-bound。所以 CPU 上做 roofline 的第一目标是回答"我的 tg 速度离内存带宽极限还有多远"，而不是算 FLOPs。

DIY roofline 四步法（无需硬件计数器）

# 1. 实测 token 速度（json 输出便于入库）
llama-bench -m model-Q4_K_M.gguf -p 0 -n 128 -r 5 -t 8 -o json

# 2. 算有效带宽：GB/s ~= 模型权重字节数 / tg 每秒
#    例: Q4_K_M 0.6B 模型约 0.4 GB, tg 60 t/s -> 24 GB/s 有效带宽

# 3. 测机器峰值带宽（一次即可，换机器才重测）
#    Intel MLC / STREAM / AIDA64 均可

# 4. 带宽利用率 = 有效 / 峰值
#    >= 80%: 已到带宽墙, 只能降精度或减 KV
#    < 60%: 有免费午餐, 查线程数/-t、NUMA、量化档位、热节流

要真正画 roofline 图（算术强度 = FLOPs/Byte）

平台工具取什么计数器
Linuxperf / LIKWIDLIKWID 的 FLOPS_* + MEM 组可直接输出 roofline 点；perf 取 cache-misses、带宽事件
Windows/x86Intel VTune（HPC Characterization）Memory Access 分析给带宽利用率和 stalls；VTune 可直接显示 roofline 视图
Windows/AMDuProf对应 AMC/带宽计数器
NVIDIA GPUNsight Compute每个 kernel 的 achieved vs peak；Nsight Systems 看时间线空隙

注意：llama.cpp 官方没有内置 roofline 工具——不要去找不存在的命令。仓内最近观测点是 llama_perf_context（include\llama.h:1680，见下节）。

三、Context window：上下文窗口评测

# 深度衰减扫描: 看长上下文下 tg 速度掉多少 (-d 为既有 KV 深度)
llama-bench -m model.gguf -p 0 -n 64 -d 0,512,2048,8192 -fa on

# 长窗困惑度 (注意 n_ctx >= 语料窗口)
llama-perplexity -m model.gguf -f longtext.txt -c 8192

# KV 占用率持续观测 (server)
curl http://localhost:8080/metrics | findstr kv_cache
关注点判定标准
tg 衰减 vs 深度FA 开启后衰减应平缓；陡降说明 KV 未量化或未走 FA fast path
kv_cache_usage_ratio持续 > 85% 会触发 defrag/K-shift（有停顿尖刺）；调 ctx 或开 -kvu 统一池
前缀复用率多轮 NLU 会话的核心收益指标：cache_prompt=true 时 verbose 日志的 n_prompt 与 prompt 长度之差即命中量
数值注意server README:500 明示——cache_prompt 下不同 batch size 的 logits 不保证逐位一致（pp 与 tg 的数值路径不同），对确定性敏感的 NLU 决策要评估该影响

四、量化退化定位五步法（核心）

# Step 1: 参考模型存 logits (一次性, 文件较大注意磁盘)
llama-perplexity -m model-f16.gguf -f eval.txt -c 512 --logits-file base-logits.bin

# Step 2: 量化模型对同一语料算 KL 散度 (读取上一步文件作基准)
llama-perplexity -m model-Q4_K_M.gguf -f eval.txt -c 512 \
  --kl-divergence --logits-file base-logits.bin
# 输出 ppl 差 + KL 散度 (perplexity.cpp:1675)

# Step 3: 分组升精度二分 (例: 只把 wv/w2 升到 Q6_K, 其余仍 Q4)
llama-quantize --tensor-type "blk\..*\.attn_v\.weight=Q6_K" \
               --tensor-type "blk\..*\.ffn_down\.weight=Q6_K" \
  model-f16.gguf model-mixtest.gguf Q4_K_M
# ppl/KL 明显回升 -> 敏感组命中; 逐组收缩范围直到单层单张量

# Step 4: 用校准数据重跑 imatrix, 观察逐层重要性行的分布陡峭度
llama-imatrix -m model-f16.gguf -f calib.txt -o imatrix.gguf

# Step 5: 工件核对 (确认混合 dtype 真的生效) + 数值级对比
python -m gguf.scripts.gguf_dump model-mixtest.gguf   # 逐张量 dtype 清单
python -m gguf.scripts.gguf_hash model-mixtest.gguf   # 工件指纹入库

五、集成过程中的辅助设计（要不要加？加什么？）

结论：要加，但分层加——观测走零成本通道常开，诊断钩子按需开启，定位工具留在离线。这也符合 llama.cpp 自身"零运行时分配"的克制设计哲学。

级别辅助设计实现点成本
P0日志接管：llama_log_set 回调把内部 timing/警告转投网关日志（结构化+trace id）llama.h:1671近零
P0性能计数导出：周期采样 llama_perf_context，导出 pp/tg 延迟直方图；生产可用 no_perf 关闭llama.h:1680近零
P0走 llama-server 时：/metrics 接 Prometheus + Grafana（kv 占用/并发/请求延迟全都有）；容量规划用 bench.py 压测server-http.cpp:61近零
P1质量回归护栏：NLU golden set + --kl-divergence 进 CI，量化工件更换/版本升级自动比对（与 qwen3-nlu-replay 夹具天然衔接）perplexity.cpp:1675中（跑分时间）
P1诊断模式开关：注册 eval_callback 逐算子计时 + copy_callback 拷贝开销，用配置项开关（回调有开销，别常开）ggml-backend.h:373中
P1超时与取消：abort_callback 接入网关请求超时；避免慢请求占住 slotgraph_compute abort 机制低
P2后端一致性巡检：ggml_backend_compare_graph_backend（ggml-backend.h:448）对比 CPU vs GPU 数值一致性，硬件适配回归用官方 API中
P2工件指纹：每次部署跑 gguf_hash.py 记录 SHA，退化先排除"模型文件悄悄变了"gguf-py\gguf\scripts\低

对应到你的 WTP184 网关：P0 三项建议直接进第一版集成；KL 回归护栏与 nlu-replay 夹具合并后，就是"模型质量门禁"的完整闭环。
