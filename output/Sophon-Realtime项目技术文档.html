1项目定位与核心概念

Sophon-Realtime 是一套开源全双工（full-duplex）语音对话模型：模型在你说话时持续监听，判断你何时说完、是否只是附和、是否还在思考；回复自带语气（笑声、叹气、重读），并可被随时打断。它属于 S2S（Speech-to-Speech，语音到语音）路线——区别于传统"ASR → LLM → TTS"三段式流水线（注意与 NLP 里的 seq2seq"序列到序列"是缩写撞车，语境不同）。

概念含义
全双工听说同时进行：你说到一半它已在起草回答，你打断它立刻停，可像真人打电话一样抢话
副语言理解不只听"说了什么"，还听"怎么说"：情绪、重音、讽刺、笑声、叹气
共享大脑三种 build 共用同一个模型（32B 或 4B），负责听音、判断话轮、写带声音标签的回复
声音标签回复中的 [laughter]、[sigh]、<strong>…</strong> 等标记，由语音层"演出来"，不会被念成文字
DuplexJev同团队开源的"语音决策模型"，即共享大脑里的听觉/判断部分，一次前向回答话轮、情绪、重音等所有决策（92ms）
架构核心思想（源码 docstring 原文翻译）："框架管会话、音频接入、VAD 和打断；话轮由 DuplexJev（stage 0 模型本身）决定"——即能量 VAD 只回答"何时该问"，语义模型回答"该不该接"。

4话轮判断：DuplexJev 的具体实现

核心不是规则，而是把话轮判断做成一道四选项选择题，让大脑模型用一个 token 回答，再用 logprobs 取概率：

问题：用户现在处于什么话轮状态？
A. 话说完了，可以接话        B. 句子没说完，还在继续
C. 简短附和，不是要接话      D. 还在组织语言，或要求先等一下
（附上下文：助手刚才说的话 + 用户音频 <|audio|>）
→ max_tokens=1, temperature=0, logprobs=20，softmax(A..D) 得 P(finished)、P(backchannel)

三个关键工程决策：

  • 选项顺序按请求哈希随机排列（blake2b 的 perm_of），防止模型偏向固定位置——与其 benchmark 评测的 option rotation 是同一手法。
  • 话轮检查不走框架 append：每次 append 会推进 turn/fence 状态，与正在播放的回复冲突；因此后台线程直接 HTTP 调本服务 stage 0 的 /v1/chat/completions，且 proc.py 识别 sophon_kind=check 请求只出一个字母、不进 talker。
  • 中英双语模板：问题以 TPL["zh"|"en"] 渲染，附"助手刚才说的是…"上下文（被切回复则用截断文本）。

5打断（barge-in）机制与历史截断

打断检测是双层的：引擎层由框架 server_vad 的 barge_in_on_speech 触发；GPT-Live 网关层自备 20ms 能量 VAD（有声 ≥200ms 且正在播放 → 丢弃播放队列），因为 GPT-Live 客户端期望服务端主动闭嘴，而引擎只裁历史不停播放。

截断的核心数据结构是回复完成时记录的 last_play = {t0: 播放起点, dur: 音频总时长, entry: 历史条目, text: 完整文本}。关键在于"实际听到多少"不是精确已知的，是估算的：

played = now − t0 − 0.25s        # 0.25s = VAD 起说话检测滞后(~0.1s) + 客户端缓冲(~60ms) 等补偿
n = len(text) × played / dur     # 文本按播放进度比例截断
a_text = text[:n] + "……（被用户打断）"
a_audio = a_audio[: played×SR]   # 音频截到已播秒数；played > 0.5s 才保留，否则整段丢弃

网关层的配套机制：播放泵以 100ms 帧外发音频并累计 played_s；transcript 按"中文 4.5 字/秒、英文 14 字/秒 + 前导时间"释放字幕；_drop_playback 时把所有回复的文本截到已释放字符。用户语音缓冲最多保留 30s；回复开始时立即结算用户段并转写（不足 0.24s 有声则不转写）。用户段起点/终点按帧 RMS 定位并前后各扩 0.2s。

6上下文管理

历史条目的数据结构（整套设计的精髓）：

history[i] = {
    "user":    np.float32 音频,          # 本轮用户语音，进 prompt 时用 <|audio|> 占位
    "a_audio": np.float32 音频 | None,   # assistant 侧优先存"实际合成播出的音频"
    "a_text":  str,                      # 截断/打断时降级用的文本
    "chain":   [ {results, a_text, a_audio, tool_calls} ],  # 工具调用链（最多 MAX_STEPS 轮）
}
  • assistant 历史优先用音频本身：完整播出的回复以 <|audio|>（带真实音频）进下一轮 prompt——语气、笑声等副语言信息因此能跨轮保留；被打断的回复降级为截断文本 + "……（被用户打断）"标记。
  • 滑动窗口：最多 8 轮或用户语音累计 120 秒，超限丢最旧——按"用户侧时长"而非 token 数裁剪，对语音模型是更贴谱的预算单位。
  • 会话开始可注入文本历史（GPT-Live 的 session.start input / extra_body.history）。
  • 系统提示词（中英双语）核心约束："只写要说出口的话，不要写括号说明、表情或格式符号；数字、日期、金额、符号和英文缩写都直接写成口语念法；需要时可以用声音标签表现笑声、咳嗽和重读。"——Tag build 的写标签 LoRA（tl2）依赖该提示词，缺失时标签产出显著减少。

域 1：信号/能量域（VAD 与打断检测）

9.4 设计观察：一个神经公式 + 一群 O(1) 启发式

这套公式体系有清晰的分层哲学：全场只有一个"神经公式"（#13 受限 softmax），其余全是 O(1) 的廉价启发式。信号域用能量 + EMA 噪声底（#1–3），时间域用线性比例估算（#7–8），决策域用分段常数阈值（#14）——工程侧刻意不做复杂建模，把"智能"全部外包给那一次 92ms 的 forward，自己只做"消费概率的确定性策略"。这与"NLU 网关管状态、模型管语义"的分层是同构的设计观。

11.2 部署形态决策

成本从零到高的推荐顺序：托管 API 试听效果 → 租一张 24GB 卡跑 Flash-4B 验证业务 → 生产上 32B（80GB）。具体决策点：

  • build 选择：表现力选 Tag、单卡并发选 Flash（40 路）、最低首音选 E2E（0.25s）——见第 2 章对比表；
  • 多 GPU 横向扩展：无内置分布式，每 GPU 一实例（GPU=1 PORT=8001 …）挂负载均衡；
  • 大陆网络优化：PIP_INDEX_URL=https://mirrors.cloud.tencent.com/pypi/simple bash install.sh；权重下载走 ModelScope（--source modelscope）；
  • 复用已下载权重：SKIP_DOWNLOAD=1 MODEL_DIR=/path/to/model bash install.sh；
  • 从 v1.1.0 及更早两卡版升级：权重需重新下载（新版含 talker220/ 目录，旧 talker/ 不再需要）；
  • Live 网关分离：网关与引擎可分机部署，BUILD=tag PORT=8000 LIVE_PORT=8780 bash start_live.sh。

11.3 E2E 三服务架构（同卡三进程 + MPS）

E2E build 在单卡上以三个本地服务运行：

服务职责默认端口

CUDA MPS 是 E2E 性能关键：scripts/start.sh 自启 MPS daemon，让 thinker 与语音引擎同时用卡；无 MPS 时两进程轮流占卡——首音从 0.25s 退化到约 0.6s，并发显著下降。首次启动约 5 分钟（载权重 + 语音引擎捕获 CUDA graph），勿误判为挂死；stop.sh 会连同自启的 MPS daemon 一起停；日志在 logs/。

WebSocket API（/ws）事件流：客户端发 {"type": "config", "lang": "zh"|"en", "history": true} → 持续发麦克风二进制帧（16kHz 单声道 PCM16，任意块大小，demo 每帧 512 样本）→ 服务端返回 turn_commit（判完话轮开始回答）/ text（回复文本，含声音标签——演出不朗读）/ 音频二进制帧（24kHz 单声道 PCM16）/ barge_in（你开口了，停止播放）/ metrics + done。一次性测试/跑分用 {"type": "turn", "audio_b64": "...", "lang": "zh"}。

12增强与微调操作指南

本章回答"如何在现有模型基础上做增强"。依据官方 finetune/README.md（ms-swift 路线）与 DuplexJev 训练配方整理。先明确术语：本章"增强学习"指在现有模型基础上继续训练/微调；严格意义的强化学习（RL）见 12.6。核心结论：四个层次的增强，从零成本到高成本依次是——运行时扩展（不改权重）→ LoRA 微调大脑（官方路径，一张 80GB 卡）→ 按 DuplexJev 配方自训决策模型 → 强化学习（官方未用）。

12.1 路径选择：先对号入座

目标路径成本
改人格/语气/领域话术/工具调用习惯B：LoRA 微调 thinker1×80GB GPU，几百条样本起步
新增一种决策类型（如车机特有场景判断）A：运行时声明问题（一行文本）零
提升话轮判断在特定噪声环境下的准确率C：DuplexJev 配方自训高（要数据+训练框架）
修 encoder 听不好的语言B 的边界情况（见 12.4 新语言警告）中，且当前无法部署

12.2 路径 A：零训练增强（先试这个）

DuplexJev 的 readout 机制让"新决策 = 运行时一行文本"——声明 Question("id", "问题文本", [选项...]) 即可，无需重训。但注意问题措辞要贴训练契约的句式（"Is there X in this audio?" / "What should it do?" 这类），且选项必须保留 "none"。系统提示词、注入历史（extra_body.history）、delegation 后端也都是不动权重的增强手段。

12.3 路径 B：LoRA 微调大脑（官方路径）

官方 finetune/ 目录提供完整操作链（在 ms-swift 4.6 / peft 0.20 / transformers 5.17、H100 实测）：

# 1. 环境
pip install "ms-swift>=4.6" "peft>=0.20,<0.21" "transformers>=4.51,<5.20" librosa soundfile

# 2. 下载底座 + tag LoRA，并重标记为 ms-swift 可续训格式
modelscope download --model AdventistsAI/Sophon-Realtime-v1 --include 'base/*' 'adapters/*' --local_dir Sophon-Realtime-v1
python -m sophon_swift.adapters to-swift Sophon-Realtime-v1/adapters/tag tag_swift

# 3. 训练（关键：--adapters tag_swift 续训 tag LoRA，rank 固定 16 / alpha 32）
CUDA_VISIBLE_DEVICES=0 swift sft \
  --custom_register_path sophon_swift/swift_register.py \
  --model Sophon-Realtime-v1 --adapters tag_swift --tuner_type lora \
  --torch_dtype bfloat16 --dataset my_data.jsonl --max_length 4096 \
  --num_train_epochs 2 --learning_rate 5e-5 \
  --per_device_train_batch_size 1 --gradient_accumulation_steps 8 \
  --gradient_checkpointing true --freeze_vit true --freeze_aligner true

# 4. 导出 + 部署（替换原 tag LoRA 的位置）
python -m sophon_swift.adapters to-vllm output/vx-xxx/checkpoint-yyy my_lora
SOPHON_MODEL_DIR=$PWD/Sophon-Realtime-v1 SOPHON_REPLY_LORA=$PWD/my_lora bash ../scripts/start.sh

数据格式（ms-swift jsonl，用户轮用 <audio> 占位，16kHz 单声道优先）：

{"messages": [
  {"role": "system", "content": "你是车载语音助手……需要时可以用声音标签表现笑声、咳嗽和重读。"},
  {"role": "user", "content": "<audio>"},
  {"role": "assistant", "content": "导航已切换到<strong>回家</strong>路线，预计三十分钟后到达。"}
], "audios": ["data/0002.wav"]}

多轮对话每一用户轮都可用 <audio>；assistant 历史可以是文本，也可以是它实际说出的音频（仅作上下文、不参与训练）。工具调用走 Qwen 格式（schemas 进 tools，调用写成 assistant 回复，结果以 role: tool 返回）。

五个决定成败的坑（全部来自官方文档）：

#坑对策
1必须续训 tag LoRA，不能新开--adapters tag_swift；新开 LoRA 会让模型停止写声音标签
2系统提示词必须以标签句结尾"需要时可以用声音标签……"是 tag LoRA 的训练契约；部署时用与训练相同的提示词
3私有数据标签密度低 → 标签退化混入官方 tag replay 数据集（8,797 条合成对话，约 1/3 带标签），占样本量 20–30%：--dataset my_data.jsonl 'tag_replay/train.jsonl#2000'
4禁止 merge LoRAthinker 和 talker 共享同一份底座权重，merge 会改变 talker 读到的东西且多吃 32GB 显存；服务端本来就按请求挂 LoRA
5音频侧（encoder/projector）本版不可训--freeze_vit --freeze_aligner 必须保持 true；强行训了 to-vllm 也会拒绝导出（拒绝含 modules_to_save 的 adapter）

硬件实测：H100 单卡峰值约 65GB（2048 token 样本、batch 1）；双卡切分后每卡约 34GB。几百条样本用 lr 2e-5~5e-5、1–2 epoch。

回归检查（官方给了现成工具 tools/regress.py）：起双 LoRA 并排服务（vLLM --enable-lora --lora-modules tag=... mine=...），对 held-out 音频对比标签率、畸形标签数、错误语言回复数、回复长度、相同回复数——标签率要贴近原版，畸形标签和错语言必须近零：

python tools/regress.py --url http://127.0.0.1:8000 --data my_eval.jsonl --base tag --new mine

12.4 路径 B 的边界：新语言警告

LoRA 只能让模型写出"它已经听得见"的语言；encoder 听不准的语言，LoRA 只会产出"流利但同音错词"的文本（官方希腊语案例：FLEURS WER 59.5%→45.8%，没治本）。训练 projector/encoder 在 ms-swift 里技术上可行（adapter 配置加 "modules_to_save": ["multi_modal_projector"]），但当前结果无法部署：to-vllm 拒绝含 modules_to_save 的 adapter，服务端只挂 LoRA 权重。官方计划 v2 后提供音频侧训练与导出路径。Talker 只说各 build 列出的语言；其他语言可给 thinker 配外接 TTS。

12.5 路径 C：按 DuplexJev 配方自训决策模型

如果目标是把话轮判断适配到特定噪声域（车载、客服电话等），复刻 DuplexJev 三阶段配方比微调 Sophon 更对症：

  1. 底座：Qwen3-ASR-0.6B encoder（冻结）+ Qwen3 小底座语言模型（冻结）+ 可训 connector（MLP 投影）+ rank-16 LoRA——用 patched Ultravox 训练框架；
  2. 阶段一：目标语言 ASR 语料做内容蒸馏（中文可用 WenetSpeech/GigaSpeech 子集）；
  3. 阶段二：用自有对话数据标注 turn state 四类（说完/没说完/附和/在想）——这是唯一必须自建的数据，schema 就是那道选择题；情绪/场景标签可按需扩展；
  4. 阶段三：混合训练保内容（内容权重 ×10，决策 ×0.5~1）；
  5. 评测：held-out 标注集 + eot-bench 风格（300ms 窗口 false cut-off 率）做回归门禁。

噪声域数据要覆盖目标场景的特有干扰（车载：发动机噪声、音乐背景、多说话人、方言口音）——这正是通用 checkpoint 最弱、自训收益最大的地方。标注量参考：Easy-Turn 规模（万级标注片段）即可起步。

许可红利：32B 大脑主体 Apache-2.0，但 -Emotion-/-Para 系 connector 权重因 ESD（research-only）为 CC BY-NC 4.0——商用场景走路径 C 自训 connector 可绕开这个许可雷区，是自训的额外收益。

12.6 路径 D：强化学习（明确边界）

官方公开配方没有 RL，三阶段全是监督学习。RL 化的可行方向：用 Full-Duplex-Bench 风格的模拟器对"接话时机正确率"发 reward（打断率/抢答率/附和误判率可从日志自动统计），对 LLM 部分做 GRPO。风险：奖励 hacking（模型学会"永远不接话"来做到零打断）。建议顺序：先跑通监督微调 + 用真实日志做离线评测，积累几万条在线交互数据后再评估 RL 的投入产出。

12.7 最小行动方案

  1. 先拿 200~500 条目标场景对话（文本即可起步，音频更佳）按官方 jsonl 格式整理；
  2. 单卡跑路径 B 验证人格/话术适配；
  3. 并行启动 turn state 四类标注（路径 C 的核心资产，标注一次两种路径都能用）；
  4. 用 tools/regress.py + 自建 held-out 集做回归门禁。

14创新点总览与副语言决策机制

本章回答两个问题：这个工程的创新点到底是什么；以及"情绪、语调"这些策略具体如何影响决策。

14.1 创新点总览

层面创新点与传统方案的差异
架构共享大脑 + 可换发声层：三种 build 只在"文字→声音"这最后一段分叉，听说/判断/写回复完全共享传统 ASR/LLM/TTS 三段各自独立，语气信息在转写环节就丢失
框架/插件分层：vLLM-Omni 管会话、fence、能量 VAD；duplex.py 插件管全部对话语义（约 1085 行单文件收敛）语义与基础设施解耦，对话策略可整体替换
算法话轮判断 = 四选项单 token 选择题 + logprobs：max_tokens=1 读出 P(finished)，92ms 完成；选项顺序按请求哈希随机排列防位置偏置传统 endpointing 是固定静音阈值；能量 VAD 只答"何时问"，语义模型答"该不该接"
检查点 × 阈值衰减：0.2s/0.95 → 2.0s/0.25，把"人类等待耐心"编码成时间-置信度退火曲线单一阈值要么抢答要么迟钝
副语言直接进决策输入：话轮问题和回复生成吃的都是 <|audio|> 原始音频，不是转写文本（见 11.2）情绪/犹豫/讽刺在 ASR 转写环节就会丢失
机制投机起草 + gen 计数器：静音 0.05s 即起草，用户一开口 gen+1 作废所有在途判决——乐观并发模式无需加锁排队
"已听到才入历史"不变量：打断按播放进度估算截断，历史永远等于双方真实听到/说出的内容传统方案要么留全文本（不诚实）要么全丢（丢信息）
三级恢复（merge&abort / BC_RESUME / 新话轮）："抢答错了""用户只是附和"是状态机一等公民传统方案把打断一律当新请求
表示assistant 历史优先存音频本身，语气跨轮保留；按用户侧秒数（120s）而非 token 裁剪token 预算对语音模型不贴谱

14.2 副语言如何影响决策：一条输入，四条路径

关键认知：DuplexJev（大脑的听觉部分）的输入永远是原始音频，不是文字——语调信息不需要任何专门管道，它天然包含在每一次 forward pass 里，在四条路径上分别起作用：

14.3 语调改变决策的具体例子（路径 A 详表）

话轮问题的上下文构造是 用户说：<|audio|>——送进 stage 0 判断的是原始音频，不是文字。同样是"用户停下来了"，语调不同，P(finished) 完全不同：

听到的声音大脑的判断决策后果
语调干脆、降调收尾P(A 说完) 高≥0.95 时 0.2s 就接话
拖长的「嗯……」「那个……」犹豫声P(D 还在想) 高即使静音到检查点也不接话，继续等
说话中一个短促的「嗯」「对」P(C 附和) ≥ 0.5 且 > P(说完)不当新请求处理，触发 BC_RESUME 续讲被切断的回复
生气地打断P(finished) 高 + 情绪信号进路径 B回复的语气和内容都会变

传统链路里 ASR 一转写，犹豫声变成"嗯"两个字，语调信息当场蒸发——后端再怎么分析也只能看到文字。这就是"情绪不是被识别出来再上报，它就是概率分布的一部分"的含义：副语言 48.6 分能直接转化为对话体验的原因即在于此。

路径 B 的佐证：flash 版 duplex.py 删掉了 tag 版的 SYS 提示词常量（写标签 LoRA tl2 的训练提示词），标签产出会显著减少——"情绪→声音标签"是训练出来的直接映射，而非外挂的情感分类器。

15DuplexJev 架构与训练原理

第 14 章讲了语调"在哪些路径上起作用"，本章回答更底层的问题：模型凭什么能听出语调，并把它变成决策概率。依据 DuplexJev 仓库（github.com/adventists-ai/duplexjev）README 的一手材料整理。核心结论："听懂语调"靠输入设计 + 训练解决；"何时接话、如何恢复"等决策策略是纯工程代码——模型提供概率，策略消费概率。

15.1 绕过文字瓶颈的架构

传统链路为什么丢语气？因为 ASR 解码成文字那一步是有损压缩：encoder 的隐状态里本就包含韵律、情绪、犹豫等信息（它们是识别文字的辅助声学特征），但解码只保留"说了什么字"，其余全部丢弃。DuplexJev 的做法是不解码，直接把隐状态投影进 LLM：

15.2 为什么"冻结 encoder + 冻结 LLM + 只训 connector"就够

原理上是两个空间之间缺一座桥的问题：

  • Qwen3-ASR-0.6B encoder（冻结）：它为了做语音识别，隐状态里必须同时编码"说了什么字"和"怎么说的"——韵律、能量、停顿这些声学特征是它识别文字的辅助信息，本来就在最后层隐状态里。传统链路的浪费在于：解码成文字只取走了前者，把后者扔了。
  • Qwen3-VL-32B 语言模型（冻结）：已经懂语言、懂问答、懂"问题+选项"格式。
  • connector（唯一可训练 + Turn 模型 rank-16 LoRA）：一个 MLP，只学"把音频隐状态投影到 LLM 嵌入空间"。训练量极小，但桥一通，冻结 LLM 的全部语言能力就直接作用于音频表示。

这就是"输入设计"那半个答案：韵律信息不走文字管道，从隐状态直通 LLM。

15.3 三阶段训练配方

阶段数据目标作用
① 内容蒸馏Ultravox v0.6 混合语料（WenetSpeech、GigaSpeech、Common Voice、CoVoST2、LibriSpeech、MUSAN…）transcript distillation教会 connector"投影要保内容"——桥不能只传情绪丢了语义
② 决策交叉熵turn state：Easy-Turn 四类（complete/incomplete/backchannel/wait）；emotion：ESD+CREMA-D 四分类（neutral/happy/angry/sad）；gender：AISHELL-1/LibriSpeechreadout 位置单个选项字母的交叉熵把"听出语调→选对字母"直接训练成模型行为
③ 混合训练①+② 混合，4,000 步，lr 1e-4，内容权重×10、gender/emotion×0.5联合优化防止学决策时遗忘内容理解

两个关键细节：

  • 问题措辞是训练契约：README 明确警告 "these are the wordings the models were trained on; always keep a 'none' option"——运行时声明的问题必须匹配训练措辞。这就是 Sophon 源码里 TPL 模板逐字保留的原因；也是"新增一种决策 = 运行时一行文本"（声明问题+选项）而无需重训生成逻辑的原因。
  • 情绪是分类题不是开放理解：emotion 在 ESD/CREMA-D 这类表演性语音库上训成四分类，真实场景的复杂情绪是泛化结果——副语言 48.6 分很强，但要知道能力边界。许可提醒：ESD 为 research-only，因此 -Emotion-/-Para- 的 connector 权重为 CC BY-NC 4.0，商用前需单独核对（32B 大脑主体仍为 Apache-2.0）。

15.4 P(finished) 的推理机制与 92ms

推理链路：[音频 token] + [助手刚才说的话] + [问题] + [选项A..D] 一次 forward，不做任何解码生成——直接在选项字母位置读 next-token softmax，归一到四个字母得 p(A..D)。92ms 的来源：prefix（音频）编码一次共享、多个问题打包进同一行用 block-diagonal mask 隔离、vLLM prefix cache 复用音频前缀、0 步解码。对比级联方案（ASR 411ms + LLM 生成 JSON 1,567ms），快约 20 倍的根本原因是把生成问题改造成了读出问题。

选项顺序 24 种排列实测：答案仅在 3.3% 的排列中改变，且集中在不确定样本；置信度 ≥0.8 时变化率 0.01%——这给了工程侧"阈值决策"统计依据（Sophon 才敢在检查点上挂 0.95→0.25 的衰减阈值）。

15.5 学到的 vs 工程的：完整能力边界表

归属能力实现方式
学习侧（训练 + 输入设计）听出语调/情绪/犹豫/重读ASR 隐状态直通 + 决策交叉熵训练

准确表述：感知与概率是训练出来的（输入设计决定信息不丢，训练配方决定映射正确）；策略与恢复是代码写出来的（消费概率做决策）。Sophon 的完整能力 = 学习侧提供"概率神谕" + 工程侧提供"对话策略"。

15.6 对端侧路线的参考价值

DuplexJev-4B = Qwen3-4B + Qwen3-ASR-0.6B encoder，约 10GB，单个 turn 问题 40–80ms，Smart Turn 92.9。"冻结小底座 + 只训 connector/LoRA"这条路已被验证能在 4B 规模跑出可用水平——与 Qwen3-0.6B 端侧评估属同一家族思路。若车机端要升级 endpointing，"Qwen3-ASR-0.6B encoder + Qwen3 小底座 + Easy-Turn 式四分类训练"是可直接对标落地的技术路线，比端侧跑完整 S2S 现实得多。

16工程借鉴（P0/P1/P2）

面向"ASR + NLU 网关 + TTS"式传统链路（如车载 NLU）的对照借鉴：

级别机制映射与理由
P0committed history ≡ 用户真实听到的内容这条不变量 + last_play{t0,dur} 播放进度估算（played = now − t0 − 补偿）TTS 播报被打断时的上下文截断：比"保留完整已合成文本"更诚实、比"全部丢弃"更保信息；估算而非精确对齐，实现成本极低
P0gen 计数器作废在途判决 + append reservation 15s 超时回滚 + 重发上限 3 次同会话幂等/并发控制的乐观失效模式：新事件一到，旧 in-flight 结果一律作废，无需加锁排队
P1merge & abort（2s 抢答窗口）+ BC_RESUME（附和则续讲）"系统抢答"与"用户嗯了一声"是两类完全不同的恢复路径，值得在网关层显式建模，而非统一当新请求处理
P1检查点 × 阈值衰减 + 单 token logprobs 话轮分类 + PERIODIC 噪声鲁棒模式纯 VAD endpointing 的升级路线：能量 VAD 管"何时问"、轻量分类器管"该不该接"；车载噪声环境尤其需要
P2assistant 侧历史存真实音频、按用户侧秒数（120s）而非 token 裁剪文本网关不必存音频，但"按时间预算裁剪历史"的思路对历史上下文持久化有参考价值
端侧可行性判断：4B 仍需约 21GB 显存，32B 需 80GB——车机端侧跑 S2S 目前完全不现实。真要在车上做全双工，现实路径是云端 S2S + 端侧轻量唤醒/打断检测的混合架构；车载场景优先关注其 Flash build（并发最高、延迟 0.31s）与打断后上下文裁剪机制。
