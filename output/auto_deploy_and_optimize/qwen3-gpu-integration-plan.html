1. 建议路线：现有 llama.cpp 增加 GPU 后端

此处是建议，尚未替用户确定硬件后端。第一阶段优先复用现有 provider、GGUF、模板、NFC、解析和 callback，只改变模型计算后端。这样能利用已经完成的 CPU 验证，并把新的差异集中在硬件执行层。

路线适合的目标新增成本 / 当前定位
A · 原生 GPU（建议首选）C++ 本机推理、单设备验证；保留现有 hook 与模型格式。新增 GPU SDK/驱动、设备选择、显存、同步和失败处理；本计划详细展开这一条。
B · GPU 服务已有 HTTP 架构，或需要把 GPU 与多个客户端共享、独立扩容和调度。复用 V3 HTTP 请求/解析层，但引擎、服务端模板、模型格式、排队和部署生命周期都要另验；服务不一定与客户端同主机。

已有 LMDeploy 路线可以作为 B 的基础，不能把当前运行的 nlu_v10 权重当作 checkpoint-8343。比较 A/B 时同时改变引擎和传输方式，结果应称“部署方案比较”，不能全部解释为 GPU 相对 CPU 的收益。服务 API 文档。

设备选择CPU / GPU：决定支持的计算在哪里执行。
权重表示F32 / Q8：决定权重如何保存和计算；两种设备都需验证各自支持情况。
接入方式进程内 / HTTP：决定故障、调度和运行时边界。

不因为使用 GPU 而重训模型，也不在本阶段更换 checkpoint、重写业务 parser、引入多 GPU、跨请求动态 batching 或加入 Q4/Q5。CPU 比较基线继续保留；是否最终采用 GPU 由正确性与实测收益决定。

4. 分阶段实现，每一步留下可复核证据

阶段工作通过条件
G0 · 定义目标与预算在 10.1.120.40 复用环境记录、补齐只读采集，记录 GPU/后端、内存上限、总调用/耗时上限和目标。引用 v7 CPU DONE 与原始结果身份。选定一个后端；将“探索性测量”与“正式性能达标”区别写清。
G1 · 构建候选同一个 SDK pin + NFC patch；独立 GPU build/install 目录。沿现有 canonical runner 增加必要选择能力，不创造平行的无监控执行流程。编译、链接、运行库闭包及 device enumeration 通过；确认实际装载的整组 libllama/GGML 和后端库身份。
G2 · 设备加载与放置核对设备可见性，加载 F32，记录 offloaded 层/张量及已分配缓冲的位置和大小；本阶段不生成。加载与实际放置符合计划。分配显存只证明加载/放置，尚不证明 GPU 已执行推理；缺少设备时明确失败。
G3 · 输入与模型无关检查在候选实际加载路径跑全部六例 reference，以及不依赖真实生成的 parser/provider 回归。字节/ID 精确一致；unknown 合法拒识、畸形响应仍失败。本阶段通过之前不执行真实生成。
G4 · GPU 执行与 F32G3 通过后运行原固定语义用例、A–B–A 与既有真实推理错误路径检查。补充实际 GPU 执行证据，与 CPU F32 对照；保存 generated IDs、raw text、停止原因、parser 语义。目标 GPU 确实执行模型计算，未静默回落 CPU；原协议、固定语义及 reset 验收通过。若不同，查有效参数、停止规则、计算精度和首个差异；必要的 HF/logits 诊断先计入预算。
G5 · GPU Q8使用同一个 Q8 GGUF，在 GPU F32 与 CPU Q8 已通过后验证。后端若不支持该格式，记录限制，不偷偷换格式。同套协议/语义/reset 门禁通过；分别记录设备影响和量化影响。
G6 · 对照测量同一主机、匹配构建模式/参数/输入输出长度，分开 cold、warm、prefill、decode 和端到端时间；观察 CPU/RAM/GPU 内存与共享负载。原始样本与方法可复核；目标已预定则判定达标，否则仅给观测值。性能结论不替代语义通过。
G7 · 形成候选交付整理 SDK/模型/配置/驱动要求、显式设备选择、受控失败处理和回退方式。保持单请求 provider 的初期边界。独立 GPU 候选可复现；产品代码接入、部署、并发扩展另有明确任务和验收。

选择设备、offload 层数和缓冲位置应在 provider 初始化处接入，通过 pin 的实际 C API 实现。不能只把 CPU 版本中的 n_gpu_layers=0 改大：还需要已编译 GPU 后端、可用设备、正确运行库及实际放置证据。

纯 CPU 对照也需要证明：GPU-enabled 构建即使层数为 0，也可能把部分算子交给 GPU。优先使用 CPU-only 候选 SDK 作参照；如需在同一 GPU 构建里禁用 GPU，按 pin 核实设备/算子/KV offload 控制。上游 CLI 的 --device none 不能未经实现就写成现有 harness 参数。上游说明。

5. 最小矩阵：一次改变一个主要变量

比较组用途约束
CPU F32 ↔ GPU F32设备/后端影响同一 F32 GGUF、SDK 源码+补丁、协议、输入、采样/stop、上下文和构建优化等级。记录实际计算精度。
CPU F32 ↔ CPU Q8CPU 上量化影响复用 v7 已通过的 F32/Q8 与 warm 数据，不因 GPU 计划出现就无理由重跑转换。
GPU F32 ↔ GPU Q8GPU 上量化与性能变化同一 GPU 后端/设备；固定语义用例不变。F32 文件名不保证 GPU 中所有运算都为 FP32。
CPU Q8 ↔ GPU Q8实用候选部署比较同一 Q8 GGUF，完整语义/协议通过后比较端到端时延和资源。

先验证单 GPU、单请求。显存足够时以完整支持的 offload 为初始候选；不足时再评估明确的部分 offload。部分 offload 可能引入额外传输和同步，不默认越多层越快。没有数据证明收益时不扩展多 GPU 或复杂调度。

目标是在 10.1.120.40 上比较 CPU 与 GPU。先从 v7 receipts 核对已有 CPU 数据确实来自该机且条件匹配；若证据显示并非同机，则保留 v7 为历史参考，在预算内补同机 CPU timing。不同主机的差值不能全部解释为 GPU 加速。

v7 实际执行为每模型 8 个固定调用 + 10 次 warm，两个模型合计 20 次 warm。GPU 矩阵须单独登记累计调用数、warm 数、诊断额度和总时限；沿用已有资源限制，不自动把 CPU 执行额度无限复制到每种 GPU 配置。

6. 看端到端收益，而不只看 token/s

本项目最终要得到可用的 NLU 结果。建议测量边界为 请求已就绪 → 完整续写生成 → parser 完成并得到语义结果；排队时间单独记录。CPU 和 GPU 使用相同边界。对短输出，模板、分词、调度等固定开销可能占较大比例，这是需要实测的假设，不是已观察结论。

指标记录方式避免误读
Cold load / 首次调用分别记录模型加载、context 初始化、首次生成；保留 GPU 首次初始化/JIT 的影响。不要把首次开销混入所有 warm 调用，也不要把所有真实首次开销隐藏掉。
Prefill / decode分别记录输入处理时长、逐 token 生成时长，及实际输入/输出 token 数。NLU 最终等待完整输出；TTFT、decode token/s 都不能替代完整请求时延。
GPU 同步沿已确认的完成边界计时，确认设备工作已完成；若 API 仅提交异步工作，使用该 pin/后端提供的完成机制。不把 CPU 提交 kernel 的时间当成 GPU 完成时间。
Resident warm模型保持加载，但沿现有 reset 语义处理每次请求；保存原始每次数据及 min / median / max。当前 reset 测试不等同于持久复用 KV 的性能，不顺带引入历史前缀缓存。
内存与显存记录 RAM 峰值、设备内存基线/峰值、模型/KV/计算缓冲、context 大小和并发数。F32 文件约 2.39 GB、Q8 文件约 0.639 GB，只是磁盘文件大小；不是总运行内存或显存要求。
协议与质量区分 raw 文本、解析成功、业务拒识、预期语义，以及 held-out 集上的 domain / intent / slot 指标。unknown 可以是合法拒识；不能算解析失败，也不能据此宣称它一定是正确语义。
吞吐与并发以后独立定义请求到达模型、队列、会话数量、资源上限和持出质量。n_batch / n_ubatch 是 token 处理预算，不代表支持相同数量的并发业务请求。

性能构建需匹配优化等级；不要用 CPU Debug 对 GPU Release 宣称硬件收益。为实际用于计时的二进制重跑必要正确性检查。若做更多样本、稳定 p95、并发或长时稳定性，另设明确预算；现有合计 20 次 warm（F32/Q8 各 10 次）仅提供初步观察。

参考 llama-bench 的输入处理/生成测量区分。它可帮助解释引擎性能，但项目验收仍以 V3 完整调用和解析结果为准。

7. C++ 层复用与故障处理

  • 复用业务层：BuildRequest、ParseResponse、history eligibility、同步 hook / callback 和语义契约共用；设备选择在初始化配置，不增加七字段业务请求。
  • 清楚划分所有权：模型常驻；context / sampler 的生命周期沿原实现。GPU buffer 必须活到相关设备操作完成后才释放。
  • 起步保持单请求：现有 provider 不是线程安全的。GPU 不会自动让一个 context 可被并发共享；跨会话扩展另设隔离/排队设计。同 session 正常轮次由调用方/宿主保持串行；此 provider 的单请求与生命周期约束不变。
  • 显式失败：设备不可见、OOM、后端加载或执行错误保留原始原因，沿现有错误边界返回。GPU 测试不能通过静默回落 CPU 掩盖失败。
  • 回退可控：初期在进程/启动配置层显式选回已验证 CPU SDK。自动在线回退属于后续产品设计，需考虑剩余 deadline、重复执行和唯一 callback。
  • SDK 成套选择：GPU 构建可能增加后端依赖库；按实际 build receipt 成套打包，不只复制一个 libllama.so，更不能混装 CPU/GPU 不同 revision 的 GGML 库。

GGUF、SDK、运行环境分别记录身份。模型文件可以在支持该格式的 CPU/GPU 后端之间复用；二进制库通常要按后端和目标平台构建。C API 有助于隔离业务 C++ 标准，但不会消除 glibc、libstdc++、驱动、ISA 和设备兼容问题。

8. 何时算这一阶段完成

  1. CPU marker 修正后的基线可复现；GPU 使用同一模型/模板/协议/NFC 身份。
  2. 目标硬件和实际 offload 已证明，GPU F32 的输入、协议、固定语义、reset 和错误路径验收通过。
  3. GPU Q8 如果纳入本阶段，必须给出单独结果；不支持或未跑时明确写出，不宣称整个矩阵完成。
  4. 同边界、同条件的时延与资源数据已保存；对预先确定的目标给出通过/未通过。目标尚未确定时只能结题为探索性验证。
  5. 候选 SDK、配置和环境要求可复现，CPU 基线保留；产品发布、CentOS/Android 和并发规模尚未验收的部分继续单列。

独立 GPU 验证通过并不强制采用 GPU。如果实测端到端收益不足、资源竞争明显，或 CPU 已满足需求，保留 CPU 是合理选择。进一步优化应由测量显示的主要耗时决定。
